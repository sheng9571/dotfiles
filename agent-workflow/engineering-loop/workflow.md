# Orchestrator workflow

## States

NEW: record task ID, original request, project path, mode, and checkpoint. DISCOVERY: delegate to Planner; preserve decisions and material questions. PLAN_READY: present the complete current version for review. APPROVED: accept only the user's standalone PLAN_APPROVED message for the current READY_FOR_APPROVAL plan; record source and fingerprint. If multiple tasks await approval, require a task ID before assigning that message; if the approving message cannot be verified after a cross-session or cross-platform resume, obtain a fresh approval. GIT_PREP: inspect existing work, default branch, remote, and local state; switch to default branch if safe, attempt pull, and create a task branch before any project edits. IMPLEMENTING: delegate the complete approved plan to Coder. REVIEW_READY: establish a stable diff baseline and delegate to Reviewer. REVIEW_DECISION: record verdict and completed review count. FIXING: send Coder-owned BLOCKER/MAJOR findings to Coder with the same plan. BLOCKED: preserve checkpoint and report exact recovery condition. PAUSED: stop new delegation at a safe boundary, retain checkpoint and current project changes, and describe how to resume. COMPLETE or CANCELLED: report results or residual changes, then delete that task's checkpoint directory.

Use the full role handoffs. A completed Reviewer assessment of a stable target counts as one round; cap the task at three completed reviews, including initial review. Do not reset the count after a plan revision or platform switch. A blocked handoff that never produced a trustworthy review does not count. Do not automatically retry the same blocker without new evidence, user input, or an external-state change. PASS completes; CHANGES_REQUIRED within the limit routes to Coder; a material plan defect routes to Planner and new user approval; unresolved BLOCKER/MAJOR after round three blocks completion. MINOR/NIT may accompany PASS.

Do not perform Git preparation twice on resume. If a pre-existing change prevents safe switch or pull, stop rather than stash/reset/clean. Authentication/network pull failure may continue on the local default branch with stale-base disclosure; merge conflicts or unclear failure require investigation. Never run git add . Do not commit or push by default. For every completed project change, report branch name, one-line Conventional Commit message, and suggested exact push command.

## Handoffs

Common fields: task ID, original request, project path, phase, plan version/status, full plan path and fingerprint, approval evidence when required, branch, review baseline, completed review count, open finding IDs. Planner also receives confirmed decisions, current questions, and prior version. Coder receives the full approved plan, acceptance criteria, security controls, and Git/worktree state; fixes include complete assigned findings. Reviewer receives original request, full approved plan, stable actual diff, Coder report, and prior finding IDs. A summary never substitutes for the approved plan.

The roles should use current primary standards, RFCs, official specifications, and vendor documentation when applicable, together with repository evidence. The Planner translates material external contracts and risks into acceptance criteria; Coder implements and tests them; Reviewer independently verifies relevant clauses. Do not impose generic technical or security checklists on unrelated work.

## Cross-session handover

When the user requests a handover, or a pause/block/interruption needs an explanation for the next session, use the installed `session-handover` skill when available. It produces a concise narrative from current evidence; it does not run for every Planner-Coder-Reviewer role handoff or every checkpoint update. Default to a session response. Persist a copy at `.agent-runs/<task-id>/handover.md` only when requested or needed by the coordinating workflow, and keep it ignored with the task state. Do not copy the full approved plan or review notes into it. If the skill is unavailable, report that limitation and provide a minimal checkpoint-based continuation summary without claiming an independent handover artifact.

The checkpoint remains authoritative for workflow phase, plan version, approval evidence, review count, and next gate. On resume, read any handover for orientation, then verify checkpoint claims against the plan, approval evidence, Git/worktree, and actual diff before delegation. A handover cannot authorize a transition, reset review rounds, or replace the complete handoff required by a role. If it conflicts with authoritative evidence, stop dependent work and report the conflict.
## Project documentation

During planning, identify only the durable documentation needed by the actual system and change. Coder updates it alongside code; Reviewer verifies it against behavior, tests, schemas, configuration, and deployment. The goal is that an unfamiliar maintainer can understand, verify, diagnose, change, and operate the system. Include the applicable behavior and error contracts, data and migration rules, configuration names, build/test procedure, local diagnosis, deployment and production diagnosis, and rollback evidence. Use executable schemas, contract tests, and representative examples where they materially improve handoff. README, architecture, interface contract, data, development, and operations documents are examples, not mandatory filenames. The plan must include observable documentation acceptance criteria for the changed scope. Reviewer should perform an independent handoff check using project documentation and contracts, exercise documented local steps when feasible, and reconcile deployment and operational steps with actual configuration. Report any inaccessible external prerequisite or unverified production step; never claim end-to-end handoff has been proven without evidence. Missing or inaccurate required documentation prevents completion. Preserve long-lived specifications in project Git only when they have independent value; keep working plans in the ignored task directory.

## Checkpoints and cleanup

Create a checkpoint at NEW, including during planning. In a Git repository, use the repository-local exclude file found through git rev-parse --git-path info/exclude to exclude .agent-runs/ before creating it; do not edit the tracked .gitignore until the task branch exists. After approval and branch creation, add .agent-runs/ to project .gitignore if absent; this tracked rule is part of the task change. Verify no checkpoint path is tracked or staged. Update checkpoint after each material decision, plan version, approval, branch creation, implementation, review, and block. On resume verify approval, version, actual branch/diff, and finding state; an old PASS is invalid if code changed. A cross-platform resume reestablishes the target rather than assuming a live child agent continues. At completion or cancellation delete only this task's checkpoint directory. At startup, inspect only direct child task directories under the canonical .agent-runs root. Never follow directory links or delete outside that root. Clean a child only when its checkpoint has a valid task ID matching the directory and an explicit COMPLETE or CANCELLED phase; leave missing, malformed, active, paused, or blocked state untouched. Before deletion, verify the resolved absolute path is inside the project checkpoint root. Checkpoints must never be staged or tracked.

## Modes

Plan-only stops after delivering a plan without starting implementation. Review-only requires an explicit stable target and, when reviewing a workflow implementation, the full approved plan. Docs-only may be an audit or a documentation change; do not invent technical facts and verify instructions against actual project evidence. Single-role Coder or Reviewer calls still require their normal handoffs. A stop request enters PAUSED; a cancellation request enters CANCELLED. Resuming PAUSED or BLOCKED revalidates plan, approval, branch, diff, and findings before dispatch. Ordinary prompts outside this skill do not enter the loop.

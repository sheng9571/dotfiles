# Orchestrator workflow

## States

NEW: record task ID, original request, project path, mode, and checkpoint. DISCOVERY: delegate to Planner; preserve decisions and material questions. PLAN_READY: present the complete current version for review. APPROVED: accept only the user's standalone PLAN_APPROVED message for the current READY_FOR_APPROVAL plan; record source and fingerprint. If multiple tasks await approval, require a task ID before assigning that message; if the approving message cannot be verified after a cross-session or cross-platform resume, obtain a fresh approval. GIT_PREP: inspect existing work, default branch, remote, and local state; switch to default branch if safe, attempt pull, and create a task branch before any project edits. IMPLEMENTING: delegate the complete approved plan with assigned work IDs to Coder; validate items in dependency order. REVIEW_READY: establish the selected gate's stable target/baseline and evidence, then delegate to Reviewer. REVIEW_DECISION: record gate verdict, its cycle/lifetime review counts, and task cumulative count; advance work or block dependents. FIXING: send Coder-owned BLOCKER/MAJOR findings to Coder with the same plan. BLOCKED: preserve checkpoint and report exact recovery condition. PAUSED: stop new delegation at a safe boundary, retain checkpoint and current project changes, and describe how to resume. COMPLETE: require all necessary work/gates and the final whole-task gate to satisfy current approved criteria, report results, then delete that task's checkpoint directory. CANCELLED: report residual project changes, then delete only that task's state.

Use the full role handoffs. A completed assessment of a stable gate target counts as one review. The approved plan authorizes one initial cycle per planned gate, each allowing at most two completed reviews. First PASS ends that gate's cycle without a second review: a milestone gate releases its dependent work, while the final gate can complete the task only with all required work/gates and validation satisfied. After first CHANGES_REQUIRED, send assigned Coder-owned BLOCKER/MAJOR findings to Coder and review the corrected stable target. After second CHANGES_REQUIRED or unresolved BLOCKER/MAJOR, block that gate and dependent work without silently dispatching a third review or another fix for that gate. Independent approved work may proceed if it does not depend on the blocker; enter task BLOCKED when no safe approved work can advance. A blocked handoff with no trustworthy assessment does not consume a review. Do not retry the same blocker without new evidence, user input, or an external-state change. Material plan defects require Planner revision and new approval; MINOR/NIT may accompany PASS.

Budgets do not reset on ordinary resume, session/platform switch, target invalidation, or plan revision. A previously passed gate invalidated by later changes uses any remaining budget in its existing cycle; if exhausted, it needs an explicit new cycle even without an open finding. PASS ends automatic review of the current target, not its historical counters. An explicit user request for a new cycle identifies the same task and exhausted gate, authorizing at most two additional completed reviews only at that gate. A task-only request is sufficient only when exactly one exhausted gate is unambiguous; otherwise ask which gate. Revalidate approval, full plan, branch/diff, affected work, findings, and counters; record the request/source before incrementing that gate's cycle and resetting only its current-cycle count to zero. Preserve gate lifetime and task totals, prior reviews, and finding IDs. Dispatch fixes for remaining Coder-owned findings; if already fixed, establish a fresh review target instead. Material plan changes still need PLAN_APPROVED. Plain resume at an exhausted gate reports the exact new-cycle request needed; do not change IDs to evade a limit. Detailed reviews use the task cumulative round number and name the gate/cycle.

Do not perform Git preparation twice on resume. If a pre-existing change prevents safe switch or pull, stop rather than stash/reset/clean. Authentication/network pull failure may continue on the local default branch with stale-base disclosure; merge conflicts or unclear failure require investigation. Never run git add . Do not commit or push by default. For every completed project change, report branch name, one-line Conventional Commit message, and suggested exact push command.

In every user-facing task-state update, show the task ID and relevant current work/gate IDs. When entering PAUSED or BLOCKED, also show the exact next action and a copyable resume command; if the review limit is exhausted, show the separate explicit new-cycle request instead of implying resume will restart review. Report the task ID when the checkpoint is first created, so it can be found even if a later session is lost.

## Work execution and validation

Read [work-plan.md](work-plan.md) for the shared decomposition and validation contract. Planner supplies the full work/dependency graph and concentrated or milestone gate schedule before approval. Retain existing top-level phases; track item/gate state beneath them. Dispatch only ready items whose required work and review prerequisites are satisfied. Coder validates at useful boundaries and returns evidence per item; the Orchestrator owns persistent state. Do not ask for approval of each routine item or call Reviewer after each small test.

A failed required check or exhausted gate blocks affected dependents, not automatically unrelated approved work. Invalidate evidence and gate PASS when the relevant implementation, contract, or prerequisite changes; preserve history/counters and revalidate affected dependents. Conditional investigations must stop dependent implementation until material design is resolved and approved. Mock/test-environment success does not prove live integration; unavailable required verification blocks its acceptance. The last gate must examine the complete accumulated task and cross-stage integration; it may also be the last milestone gate to avoid duplicate review.

## Handoffs

Common fields: task ID, original request, project path, phase, plan version/status, full plan path/fingerprint, approval evidence when required, branch, task baseline, assigned work/gate IDs, approved dependencies, current item/gate state, validation evidence, stable gate target/baseline, gate cycle/counts, task cumulative reviews, and open finding IDs. Planner also receives confirmed decisions, current questions, and prior version. Coder receives the full approved plan, acceptance criteria, security controls, and Git/worktree state; fixes include complete assigned findings. Reviewer receives original request, full approved plan, stable actual diff, Coder report, and prior finding IDs. A summary never substitutes for the approved plan.

The roles should use current primary standards, RFCs, official specifications, and vendor documentation when applicable, together with repository evidence. The Planner translates material external contracts and risks into acceptance criteria; Coder implements and tests them; Reviewer independently verifies relevant clauses. Do not impose generic technical or security checklists on unrelated work.

## Cross-session handover

When the user requests a handover, or a pause/block/interruption needs an explanation for the next session, use the installed `session-handover` skill when available. It produces a concise narrative from current evidence; it does not run for every Planner-Coder-Reviewer role handoff or every checkpoint update. Default to a session response. Persist a copy at `.agent-runs/<task-id>/handover.md` only when requested or needed by the coordinating workflow, and keep it ignored with the task state. Do not copy the full approved plan or review notes into it. If the skill is unavailable, report that limitation and provide a minimal checkpoint-based continuation summary without claiming an independent handover artifact.

The checkpoint remains authoritative for workflow phase, plan/approval, work/dependency state, gate targets/cycles/counts, task cumulative reviews, and next action. On resume, read any handover for orientation, then verify checkpoint claims against the plan, approval evidence, Git/worktree, actual diff, affected work evidence, gate cycles, and cumulative review count before delegation. A handover cannot authorize a transition, reset review rounds, or replace the complete handoff required by a role. If it conflicts with authoritative evidence, stop dependent work and report the conflict.

## Project documentation

During planning, identify only the durable documentation needed by the actual system and change. Coder updates it alongside code; Reviewer verifies it against behavior, tests, schemas, configuration, and deployment. The goal is that an unfamiliar maintainer can understand, verify, diagnose, change, and operate the system. Include the applicable behavior and error contracts, data and migration rules, configuration names, build/test procedure, local diagnosis, deployment and production diagnosis, and rollback evidence. Use executable schemas, contract tests, and representative examples where they materially improve handoff. README, architecture, interface contract, data, development, and operations documents are examples, not mandatory filenames. The plan must include observable documentation acceptance criteria for the changed scope. Reviewer should perform an independent handoff check using project documentation and contracts, exercise documented local steps when feasible, and reconcile deployment and operational steps with actual configuration. Report any inaccessible external prerequisite or unverified production step; never claim end-to-end handoff has been proven without evidence. Missing or inaccurate required documentation prevents completion. Preserve long-lived specifications in project Git only when they have independent value; keep working plans in the ignored task directory.

## Checkpoints and cleanup

Create a checkpoint at NEW, including during planning. In a Git repository, use the repository-local exclude file found through git rev-parse --git-path info/exclude to exclude .agent-runs/ before creating it; do not edit the tracked .gitignore until the task branch exists. After approval and branch creation, add .agent-runs/ to project .gitignore if absent; this tracked rule is part of the task change. Verify no checkpoint path is tracked or staged. Update checkpoint after each material decision, plan version, approval, branch creation, item validation/failure, review, invalidation, and block. On resume verify approval, version, actual branch/diff, item evidence/dependencies, gate budgets, and findings; invalidate affected old PASS when code changes. A cross-platform resume reestablishes the target rather than assuming a live child agent continues. At completion or cancellation delete only this task's checkpoint directory. At startup, inspect only direct child task directories under the canonical .agent-runs root. Never follow directory links or delete outside that root. Clean a child only when its checkpoint has a valid task ID matching the directory and an explicit COMPLETE or CANCELLED phase; leave missing, malformed, active, paused, or blocked state untouched. Before deletion, verify the resolved absolute path is inside the project checkpoint root. Checkpoints must never be staged or tracked.

## Modes

Plan-only stops after delivering a plan without starting implementation. Review-only requires an explicit stable target and, when reviewing a workflow implementation, the full approved plan. Docs-only may be an audit or a documentation change; do not invent technical facts and verify instructions against actual project evidence. Single-role Coder or Reviewer calls still require their normal handoffs. A stop request enters PAUSED; a cancellation request enters CANCELLED. Resuming PAUSED or BLOCKED revalidates plan, approval, branch, diff, findings, item/gate evidence, and each gate's review-cycle budget before dispatch. Reaching the review limit requires a separate explicit new-cycle request; resume alone does not grant one. Ordinary prompts outside this skill do not enter the loop.

# Task checkpoint contract

Location: <project>/.agent-runs/YYYYMMDD-HHMMSS-<slug>-<short-id>/checkpoint.md. Use portable alphanumeric and hyphen characters; keep the task ID stable across versions and platforms. This directory is untracked temporary state, never a Git deliverable.

The single checkpoint.md is authoritative for current state. Start it with exact single-line fields Task ID: <directory name> and Phase: NEW | DISCOVERY | PLAN_READY | APPROVED | GIT_PREP | IMPLEMENTING | REVIEW_READY | REVIEW_DECISION | FIXING | BLOCKED | PAUSED | COMPLETE | CANCELLED. Record original request, project path, mode, next action, confirmed decisions/open questions, full plan version/status/path/fingerprint, approval message and source, branch/default branch/pull outcome, task diff baseline, and last update time with zone. Never store secrets, full logs, or duplicate conversation history.

Use the work and gate IDs in the approved plan; read [work-plan.md](work-plan.md) for their meaning. Record the selected review schedule, current work/gate IDs, and concise progress:
- Work item: ID, state, dependency/blocker, required validation results and evidence references; point to the plan for unchanged definitions.
- Review gate: ID, covered work IDs, state, stable review target/baseline, cycle number starting at 1, completed reviews in that cycle (0..2), gate lifetime review count, open finding IDs, and any explicit extra-cycle request with its source. The final gate ID and full-task scope must be identifiable.
- Task cumulative review count: all completed assessments across gates and cycles, never reset. Record exact blockers, affected dependents, independent runnable work, and next action.

Update after a material decision, plan revision/approval, branch preparation, work-item validation or failure, review, invalidation, or block. Keep the complete versioned plan separate and preserve exact approved content. Optional reviews/round-N.md holds detailed review evidence; N is the task cumulative number and each record identifies its gate/cycle. Never overwrite a prior review. Use one state file rather than one per role, phase, or work item; link larger evidence only when needed.

On resume compare claims with the actual project, approval, plan, branch/diff, work evidence, gate targets, findings, and budgets. Skip already verified work only after confirming its evidence is still applicable; do not rerun all work blindly. Changed approved content needs new approval; changed implementation invalidates affected item/gate/dependent evidence and may require fresh review. Preserve historical counts and records. Missing, corrupt, or contradictory material state blocks dependent continuation. An exhausted gate stays blocked on plain resume; only an explicit user request identifying that task/gate authorizes another cycle of at most two reviews. A new cycle changes only that gate's current-cycle count, not historical totals or another gate's budget.

Legacy checkpoints: reconstruct work/gate mappings from the approved plan and actual evidence; do not invent completed states. If an existing single-scope plan has no review gates, map its existing review scope and counters to one final gate GF, preserving targets, approval, findings, and totals. If a multi-stage plan lacks unambiguous mappings, stop and request clarification or a revised approved plan. Under the former three-review format, preserve the historical count as GF's lifetime and task cumulative count; 0 or 1 may continue in the initial cycle, while 2 or 3 exhausts it and requires an explicit new-cycle request. Preserve old fields as historical evidence until migration is reconciled; never gain budget through migration.

A blocked/paused task remains until resumed or explicitly cancelled. At completion/cancellation delete only its task directory according to workflow cleanup rules; checkpoints and temporary evidence must never be tracked or staged.
